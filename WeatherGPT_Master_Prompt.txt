2. GEMINI — CURRENT API REQUIREMENT
==================================================

As of August 2026, use the current stable Gemini model architecture rather than obsolete Gemini 1.5-era APIs.

Preferred current model:
gemini-3.7-flash

Model ID:
gemini-3.7-flash

The official Gemini API documentation currently shows the modern Interactions API and the google-genai SDK. For this PHP-only prototype, do NOT require a Python SDK. Call the Gemini REST API directly from PHP using cURL.

Preferred REST pattern:

POST:
https://generativelanguage.googleapis.com/v1beta/interactions

Headers:
x-goog-api-key: YOUR_GEMINI_API_KEY
Content-Type: application/json

Body concept:
{
  "model": "gemini-3.7-flash",
  "input": "YOUR_PROMPT"
}

The application must encapsulate this in a PHP function/service so the model can be changed later by changing one configuration value.

IMPORTANT:
Do NOT expose the Gemini API key in browser JavaScript.
Do NOT put the key in HTML.
Do NOT put the key in client-side fetch requests.
The browser must call a PHP backend endpoint, and PHP must call Gemini.

Store the key in an environment variable if Hostinger supports it.
Otherwise provide a clearly marked local configuration mechanism that is NOT committed to a public repository, and explain how to protect it.

Configuration variables should conceptually include:
GEMINI_API_KEY
GEMINI_MODEL=gemini-3.7-flash

Never hard-code the real API key in the repository.

The system must gracefully handle:
- missing key;
- invalid key;
- quota/rate-limit errors;
- timeout;
- Gemini unavailable;
- malformed response.

The UI must show a useful error rather than crashing.

GEMINI RATE LIMITING
Do not hard-code assumptions such as “15 RPM” unless the current account/model limits actually say so. Gemini rate limits vary by model and account/project. Implement application-side throttling and exponential backoff for HTTP 429/RESOURCE_EXHAUSTED, while clearly documenting that the authoritative limits are those shown in Google AI Studio for the user's project.

For a free-tier prototype:
- minimize unnecessary Gemini calls;
- do not call Gemini multiple times for every simple weather request;
- cache/refuse duplicate requests when sensible;
- use concise prompts and bounded outputs;
- keep a per-user/application request log;
- display a friendly quota message if the upstream API rejects the request.

If the account's available free-tier model differs, make the model configurable rather than rewriting the application.

5. QUERY UNDERSTANDING + SELF-REFLECT / AGENT PIPELINE
==================================================

Implement a lightweight, transparent agentic pipeline.

Do NOT create an uncontrolled infinite agent loop.

Pipeline:

STEP A — USER INPUT
Text or speech transcript.

STEP B — NORMALIZATION
Normalize language, whitespace, obvious speech recognition artifacts.

STEP C — INTENT + ENTITY EXTRACTION
Use Gemini to classify the request into a strict JSON schema such as:

{
  "intent": "weather_current | weather_forecast | weather_historical | climate | alerts | advisory | general_weather_question | general_ai",
  "location_required": true,
  "location": null,
  "time_range": null,
  "needs_web_search": false,
  "needs_weather_api": true,
  "needs_device_location": true,
  "response_language": "auto",
  "search_query": null
}

If the query is simple and deterministic, prefer local logic over a Gemini call.

STEP D — QUERY REFINEMENT
If external information is needed, create a concise search query.

Example:
User: “Will it rain heavily near me tomorrow evening?”

Internal refined query:
“tomorrow evening heavy rainfall forecast [resolved location]”

Do not expose internal chain-of-thought.
Only expose a short “What I checked” summary.

STEP E — TOOL EXECUTION
Call only the tools required:
- weather provider;
- geocoder;
- web search;
- device location;
- optional alert provider.

STEP F — EVIDENCE EVALUATION
Pass the structured weather data and search evidence to Gemini.

Gemini acts as a judge/synthesizer:
- compare sources;
- identify agreement/disagreement;
- distinguish forecast data from web claims;
- avoid inventing facts;
- prefer structured weather data for numeric weather values;
- clearly state uncertainty;
- never manufacture warnings.

STEP G — FINAL RESPONSE
Generate a concise natural-language answer in the selected language.

Return structured metadata:
- answer;
- location;
- source list;
- weather data;
- confidence;
- timestamp;
- whether location was inferred/provided;
- whether external search was used.

Do not expose hidden chain-of-thought or private reasoning.
